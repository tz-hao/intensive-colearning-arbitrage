## 一句话总结

**执行链路的本质 = 把 LI.FI 报价里的 `transactionRequest` 字段变成一笔「由我私钥签名的、广播到链上的真实交易」，然后用 `/status` 盯着它从 PENDING 走到 DONE 或 FAILED。**

## 今日核心产出

### 1. 五步链路（全部实测跑通）

```
① GET /quote         → 报价 + 顶层 transactionRequest（to/data/value/gasLimit/gasPrice）
② 授权检查           → allowance(token, owner, LI.FI Diamond) < 金额？→ 构造 approve
③ 本地签名           → eth_account.sign_transaction（离线，不碰网络）
④ 广播（可选）       → eth_sendRawTransaction 到源链 RPC → txHash
⑤ /status 轮询       → PENDING → DONE / FAILED（dry-run 时会 NOT_FOUND，预期行为）
```

### 2. 实测记录

```bash
# 主网 dry-run（真实报价 + 真实签名，不广播）

# 输出: tool=eco | 到账 9975.0000 | approvalAddress=0x1231DEB6...
```

## 关键 API 事实（08-16 实测，重要！）

1. **新版 LI.FI API：`/quote` 直接返回顶层 `transactionRequest`**，不再需要 POST `/v1/transactionRequest`（该端点已 404 废弃）。文档 end-to-end example 也确认了这个写法。
2. **approve 的目标不是"桥合约"，而是 `quote.estimate.approvalAddress`**（= LI.FI Diamond 合约 0x1231DEB6...）。任务书里说的"approve 给 LI.FI 合约，权限最小化"——**只授权所需金额**，不设无限额度。
3. **native 币（ETH）不需要 approve**，跳过第 ② 步。
4. **`/status` 只需 txHash**（fromChain/toChain 可选，加速查询）；交易未上链返回 404 → 按 NOT_FOUND 处理。
5. **状态枚举**：`NOT_FOUND`（未上链/未索引）→ `PENDING`（桥接中）→ `DONE`（成功）或 `FAILED`（失败，带 substatusMessage 原因）。
6. **LI.FI 测试网路由有限**：Arbitrum Sepolia / Base Sepolia 的 USDC、ETH 跨链 quote 全部 404（LI.FI 测试网支持不全）。**主网演示用 dry-run 最稳**——签名、授权检查、状态查询全都能真实跑，只是不广播。

### 踩坑记录（新人必看）

| 坑 | 现象 | 解法 |
|----|------|------|
| `toAmount` 是**十进制字符串**不是 hex | 10,000 USDC 显示成 659,092 | `s2i()` 用 `int(str)` 解析，别用 hex 解析 |
| 旧 `/transactionRequest` 端点 | 404 Not Found | 用 `/quote` 顶层 `transactionRequest` |
| `/status` 用假 txHash | 400/404 | 404 → 视为 NOT_FOUND 继续轮询 |
| 测试网跨链 | 404 | 主网 dry-run 演示；测试网等 LI.FI 支持 |

## 原理性理解：为什么"签名"是执行链路的灵魂？

- 你看到的"发送交易"其实是**两件事**：① 用私钥给交易内容（to/data/value/gas/nonce/chainId）做数学签名；② 把签名后的 raw tx 广播给网络。
- 签名是**离线**的——不查网络也能签；广播才需要 gas 和网络。
- 这就是为什么 dry-run 能验证 80% 的链路：签名对不对、交易格式对不对，**本地就能验证**（eth_keys 恢复地址匹配 = 签名有效）。
- 广播失败的原因主要就三类：nonce 冲突、gas 不足、approve 没到位——executor 已把这三关都做了检查。
